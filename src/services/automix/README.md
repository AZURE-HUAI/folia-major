# Automix — 智能过渡

播放器的「混音过渡」开关背后的全部实现。功能本身的代码全在这个目录里，目录外只剩下四个接线点。

单元测试在 `test/unit/automix/`，与本目录一一对应。

## 一次换歌，从上往下走一遍

| 层 | 文件 | 回答的问题 |
| --- | --- | --- |
| 证据 | `trackProfile.ts` | 这个音频文件本身是什么样：BPM（全曲 + 尾段）、小节线在哪、响度（LUFS）、两端各自的调、三段频谱占比、段落边界表、前奏到哪结束、结尾是收还是断 |
| | `signalAnalysis.ts` | 上下都要用的数学：K 计权、自相关测速、小节线定位（`estimateDownbeat`）、重拍相位、交叉曲线、分频段曲线、平衡修正 |
| | `stems.ts` | 拆轨的**窗口**：只拆一首歌的头 30 秒或尾 30 秒，缓存三个窗口，并回答「这个构建能不能拆」 |
| | `stemGesture.ts` | 第十一轮那套手法的**算术**：人声怎么退场、鼓/贝斯/其余各在什么时刻交接。纯函数，无音频节点 |
| | `beatThis.ts` | Beat This! 这个模型的**契约**：它要的梅尔频谱、分块方式、峰值挑选、以及把结果折成 `{offset, period}` 格子。**不含模型本身** |
| | `profileService.ts` | 字节从哪来、什么时候允许下载、测完存哪。`trackProfile` 的不纯的那一半 |
| | `deckAnalyser.ts` | 正在响的那一路此刻是什么样：实时电平（同样 K 计权）、下一个拍点在哪 |
| | `deckClock.ts` | 这一路**此刻播到第几秒**——把 `currentTime` 的台阶拟合成直线，精度进到毫秒 |
| 决策 | `musicalTime.ts` | 音乐的单位：拍/小节/乐句取整、两首歌速度关系（含二倍等价）、入场点对齐 |
| | `transitionChooser.ts` | 这两首歌该用四种接法里的哪一种（beatCut / bassSwap / tailRide / plainBlend），以及音色差多少、要不要抛回声 |
| | `transitionPlanner.ts` | 这一次接多长、落在出场曲的哪个位置、下一首从第几秒进 |
| | `crossfadePlanner.ts` | 另一套策略：用户设定的长度，永远同一个形状，什么都不看 |
| | `transitionStrategy.ts` | 这次换歌交给上面哪一个规划器 |
| 执行 | `automixSession.ts` | 状态机 `idle → armed → fading`，以及每一步反悔的条件 |
| | `crossfadeGraph.ts` | Web Audio 那一半：两路 deck 的节点链、增益曲线、三段频谱各自的接缝、回声抛掷 |
| | `tempoBend.ts` | 把出场曲拉到进场曲的速度上（`playbackRate` + `preservesPitch`，音高由浏览器保住） |
| 绑定 | `useAutomixDecks.ts` | React 外壳：两个 `<audio>`、当前是哪一路、每一路渲染什么 src |

除 `useAutomixDecks.ts` 外都不碰 React 也不碰 DOM，所以测试不需要音频设备。

## 两种模式是两个规划器，不是一个规划器加一个开关

`Folia Crossfade` 和 `Folia Automix` 各自是一个纯函数，各自返回同一个 `TransitionPlan`，
`transitionStrategy.ts` 只负责选一个。执行层（`automixSession` + `crossfadeGraph`）一行没改，
它从来就只认计划、不认是谁写的——**这个接缝本来就在**，两种模式是把它用起来，不是为它新加的抽象。
加第三种就是这里再加一个文件，下游一行不动。

两者的区别不是「参数不同」，是**允许看什么**：交叉淡化只看两个时长和用户设的秒数（外加两端的数字静音，
那和 duration 一样是事实不是判断），自动混音看全部离线测量。所以交叉淡化那个文件里**没有**速度、调性、
段落、人声窗口的字眼——一旦有了，它就不再是那个可预测的一半了。

**降级判据必须对着「规划器真正吃什么」写，不是对着「有没有档案」写。** 第一版写成
`from.profile || to.profile`，一分钟内就被既有测试打回来：一首没有离线档案的歌**照样有速度**——
正在响的那一路自己测的——而那个速度正是「接八个小节」和「接五秒」的差别。只看档案，
21.3 秒的乐句级过渡被换成 5 秒交叉淡化，**一个用来保护功能的判断把功能关掉了**。
现在 `hasEvidence` 三个来源一起看：任一侧的档案、任何来源的速度、出场曲的歌词时间轴。

## Beat This! —— 前处理是**契约**，不是参数

`beatThis.ts` 顶上那一串常数（22050、n_fft 1024、hop 441、Slaney mel 30–11000Hz、`log1p(1000x)`、
分块 1500 帧、边界 6 帧）**一个都不能动**。它们是那份权重训练时用的值，改任何一个，模型不会报错，
它会给出一个**很有把握的错答案**——而这正是这个项目已经栽过三次的失败方式。

**验收方式已经存在，别重新发明**：`beats.json` 是官方 Python `Audio2Beats(final0, dbn=False)`
在 30 首真实曲库歌曲上的输出，`tracks/*.raw` 是喂给它的同一份采样。这份 TS 移植跑同样的输入，
**拍点和小节线 F-measure 都是 1.0000，平均偏差 0.00 ms，每首歌连拍数都一模一样**。
速度 58 倍实时（一首四分钟的歌约 4 秒）。任何一次「格子好像有点不对」，先跑这个再改代码。

**它替换而不是修正。** 有模型时 `bpm` / `outroBpm` / `beatOffset` / `downbeatOffset` /
`headDownbeatOffset` / `beatsPerBar` 六个字段全部来自它，`estimateTempo` / `estimateDownbeat`
一行不改地留着当**回退**——浏览器版本、权重缺失、推理失败时它们是唯一的答案。
**两个估计不混用**：相位只在它被测出来的那个格子上有意义，半个这个格子配半个那个格子谁都不是。

**`fft` 从 `trackProfile.ts` 搬到了 `signalAnalysis.ts`。** 因为 `beatThis.ts` 也要用它，
留在原处就是 `trackProfile → beatThis → trackProfile` 一个真的环。按 README 自己的分层，
「上下都要用的数学」本来就该在 `signalAnalysis`。

**权重不进 git，进安装包。** 83MB 一个永远不变的文件，不该让每一次 clone 都背着它的历史；
但许可证是 MIT，分发是允许的，而拿不到 GitHub 的用户在这里是常态不是例外。
`build/fetchModels.mjs` 下载并**校验 sha256**——「下载成功」不等于「能用」，
一个被截断或被镜像替换的 ONNX 不会响，它会加载成功然后自信地答错。

## 拆轨：为什么是四条 buffer，而不是一条修正流

四条 stem 加起来就是原曲，所以理论上**只要多一条人声轨**就够了——把元素的整体增益当作「其余部分」的包络，
再加一条带符号的人声进去补差，`g_vocal = α - β`。少三条流，少一半的图。

**实测把这条路否掉了。** 那条修正流在人声要被切掉时是在做**相减**，而相减要求 buffer 和
`<audio>` 元素对齐到样本。测下来（[reference_element_buffer_alignment]）：

| 文件 | 相位取反后的对消深度 |
|---|---|
| WAV | **-222 dB**（表底，即逐样本相等），9 秒零漂移 |
| 有损（Opus） | **+3.8 dB** —— 不但没抵消，还更响了 |

原因不在编解码器（把元素的实际输出和 `decodeAudioData` 做互相关，滞后是 **0**），
而在 `el.currentTime`：压缩流上它被量化到编解码器自己的帧，buffer 就会差出一帧去。

所以：**播四条 buffer，把元素淡出**，永远不靠对消。切换用 **8 毫秒**的交叉淡化——
对齐时它是透明的，没对齐时也只是几毫秒的梳状滤波，而硬切在前一种情况下完美、在后一种情况下是「咔」一声。

`other` 用**相减**得到（`mix - vocals - drums - bass`），不是模型的第四行输出。
htdemucs 自己那四行只能重建到 -31 dB；相减让四条**精确**加回原曲，
而这正是「窗口开头四条都在 1.0 时，stem 之和与元素逐样本相同」这个换手前提所要求的。

## 推理不能待在拥有窗口的进程里

`onnxruntime-node` 的 `run()` **看起来是异步的，其实不是**。它的 JS 包装是
`new Promise(r => setImmediate(() => r(session.run(...))))`，里面那个 `session.run` 是同步的
N-API 调用——`setImmediate` 只决定这一坨阻塞从哪个 tick 开始，决定不了它是不是阻塞。
拿一个 10ms 的定时器围着一段 htdemucs 量：**该触发 150 次的地方只触发了 1 次**，模型加载期间
361 次里触发 0 次。

放在主进程里这不是「慢」，是「死」。主进程拥有窗口的消息循环和每一个 `ipcMain` 处理器，
所以事件循环被堵住 = Windows 把窗口画成「无响应」+ 渲染进程每一次 `invoke` 都排在 transformer 后面。
一首歌要 1 次 Beat This!（~5.7s）+ 2 个 30 秒拆轨窗口（~16s 和 ~10s），
**每首歌约 30–45 秒窗口完全无响应**。这就是「所有 UI 交互都卡」的来源。

所以模型搬进 `utilityProcess`。同一台机器实测：主进程最长停顿从 ~1450ms 降到 **25ms**，
主进程 RSS 从 530MB+ 降到 131MB（530MB 现在在子进程里，闲置两分钟连进程一起杀掉）。

**`intraOpNumThreads` 必须设，默认值是错的。** onnxruntime 默认一个逻辑核一个线程，
24 核机器上实测每段 3547ms——比 12 线程的 1438ms **慢 2.5 倍**，线程在自己跟自己抢。
取核数的四分之一：真正要守的量是**留给渲染帧和音频线程的机器比例**，而这个比例不该随机器大小变化。
拆轨有几分钟的提前量、没有截止时间，它不需要快，它需要看不见。

| intraOp | 每段 | 机器 CPU | 30 秒窗口 |
| --- | --- | --- | --- |
| 默认（24） | 3547ms | 51% | 21.3s |
| 12 | 1438ms | 66% | 8.6s |
| 6 | 1602ms | 42% | 9.6s |
| 4 | 1873ms | 32% | 11.2s |
| 2 | 2908ms | 19% | 17.4s |

## 两条要守住的线

**没有 `index.ts`，是故意的。** 依赖在目录层面是双向的：`prefetchService` 调 `profileService`
去测曲子，而 `useAutomixDecks` 又回头读 `prefetchService` 的歌词缓存。现在两条边落在不同文件上，
所以没有循环导入；一旦收进一个 barrel，它们就会合并成一个真的环。目录本身就是边界。

**「装好下一首」和「开始淡入淡出」是两件事。** `automixSession` 提前
`AUTOMIX_ARM_LEAD_SEC` 秒备好过渡，这段时间里 `onAutoplayHoldChange(true)` 压住播放桥的自动播放：
deck 照常拿到 src 并缓冲，只是先不出声，到点才放。把这两件事合成一件，装载耗时就会从淡入淡出里
扣掉，规划器算多长都没用。改动这一段时先确认每条退出路径都会解压——`settle` 是所有结局的必经之路。

这里有一个还没补的口子，记在这里以免下次又当成新问题查：**已经存进媒体缓存的曲子拿不到预热。**
预热要的是一个字符串，而 `playSong` 给缓存曲目现开一个 blob 地址，每次都不一样；`resolveDeckSrc`
的全部前提是「预热用的那个字符串就是最后要播的那个」，所以 `warmSrc` 对这类曲目直接给 null。
要补就得让 blob 地址在预热和播放之间共用一个，不是把 sentinel 塞进 `warmSrc` 就行。

**淡入淡出和混音的区别是形状，不是长度。** 这条被绕了三圈才找到：过渡长度从 2 秒调到 8.5 秒、
从 4 拍调到 16 拍，听感始终是「一次淡入淡出」——因为**它确实是**。`buildCrossfadeCurves` 原本对
四种接法输出同一条横跨全程的等功率余弦，三个频段只是在这条曲线**之上**加修饰。而在一条淡出曲线上
加滤波，得到的还是一条淡出曲线。

淡出的听感签名不是「长」，是**出场曲从头到尾连续下滑**，你全程都在听它退走。混音的签名是
**出场曲一直在，然后走掉**。所以 `together` 参数给曲线中段加了一段**平台**：两首歌各停在
cos(π/4) 上不动，占整段的一半，低频就在这段里换手——两首等强、只有一个低端，这才是那个 DJ 动作，
也才是它不糊的原因。

关键：**这不花任何 headroom。**平台正好落在 cos = sin 的那一点，中段合成功率和其它任何时刻一模一样。
同样的能量，不同的形状。实测两条曲线的 sum power 逐点相同。
`plainBlend` 的 `together` 是 0——纯淡入淡出本来就该是纯淡入淡出，那是它的定义。

**平衡修正是纠正母带不平衡的，不是纠正音乐动态的。** 两边必须是**同一种测量**，而它错过两次：
先是拿进场曲的实时读数（那是它故意安静的前奏）去比，被修成用整曲响度；结果出场侧仍然是**实时短窗**
——短窗在任何有动态的段落都比整曲积分值高好几 dB，于是差值里带着一个**每次方向相同的固定偏移**，
日志里 `held the outgoing track 6.0dB down` 常年贴在上限。**一个对任何输入都饱和的修正不是修正，是常数。**
现在两侧都走 `referenceDb(profile, chain)`，同一个函数、同一种量；实时探针只在没有档案时兜底，
而且两侧一起兜底。安静的前奏和衰减的尾巴是音乐，抹平它们等于删音乐。

**启发式只决定「怎么接」，不决定「接不接」。** 曾经有第五种接法 `gapless`：同专辑相邻、两端都
满电平，就用一个 6 毫秒的拼接直接对上，理由是唱片本来就连着。对唱片的判断没错，对开关的判断错了
——在一张从头连到尾的专辑上它吃掉了三分之二的换歌，于是听众打开「混音过渡」，听到的是什么都没发生。
现在剩下的每一种接法都是听得见的。加新接法时守住这条。

同一条规则的第二次违反不是靠新接法混进来的，是靠**乘法**：调性冲突 ×0.4、速度太远 ×0.5、
进场曲满电平 ×0.6，每一条单独看都对，乘起来是 0.12——那不叫「短一点」，那是一次没人写下来的硬切。
`chooseTransitionStyle` 里 `lengthScale` 现在有 0.25 的地板（一个乐句的四分之一 = 一小节，
还听得出是「接」的最短跨度）。任何新的长度系数都要记得它是要跟别人相乘的。

**一首歌结束的地方，不是文件结束的地方——而且有两个「结束」。** 过渡是从「歌尾」倒着排的，
「歌尾」一度读的是媒体时长，于是母带尾巴上的东西全被当成音乐排了进去。两次实测各暴露一层：

- `leadOut` / `soundingEnd`：最后一个音之后的数字静音。29 次换歌里 7 次交接时出场曲低于 -30 dBFS，
  4 次低于 -40——那不是过渡轻，是歌早就放完了。
- `bodyOut` / `bodyEnd`：静音门槛是「比**峰值**低 40 dB」，现代母带上那约等于比**音乐本身**低 30 dB。
  所以贴着 `soundingEnd` 排的过渡整段都在衰减里跑。补完上一条之后 5 次里仍有 3 次交接在 -23～-26 dBFS。

`planTransition` 的落点是这三句的最小值/最大值组合：`min(sounding - overlap, max(body, lastSung))`
——正常贴着响声末尾，衰减来得更早就从衰减顶点开始，但绝不早于唱完。`automixSession` 里放开 autoplay
的时刻和二次闸门的 `remaining` 必须读计划，不能再自己拿 duration 减一遍。head-only 档案两个字段都是
null（尾巴下载不到），那时才退回文件末尾。超过 `MAX_TRIMMED_TAIL_SEC` 的空白或衰减不算尾巴——
那是隐藏曲目或者写好的氛围尾奏，动它等于删歌。

**过渡长度是算出来的，25 秒只是天花板。** `AUTOMIX_MAX_OVERLAP_SEC` 曾经是 8，注释写着「再长就不像
一首歌在结束了」——那是品味不是测量，而且它比任何测出来的东西都更常成为瓶颈（日志里出现过 63 秒尾奏
配 8 秒前奏被一刀切到 8 秒）。现在长度是「一个乐句（16 拍）× 各项系数 → 按乐句/小节/拍取整」，
天花板只负责拦截，且拦截时是往下退整数个小节，不是把上限本身当答案。放开到 25 的前提是 E4（LUFS）
和 E5（重叠期留 1.5dB 余量）都已经落地——长重叠撑得住，才敢放长。

**计划要按「还剩多少」算，不是按「一共有多少」算。** `planTransition` 从歌尾倒着排，
从不看播放头在哪——默认「看到的时候还早着呢」。但 `checkTransitionPoint` 不是按时钟跑的，
它是**在没人挡着的时候**才跑：上一次过渡在响的整段时间里它被 `getPhase() !== 'idle'` 挡在门外，
duration 还没到位时也被挡在门外。于是对一首歌的**第一眼**完全可能落在它自己的交接点后面几秒，
而按整条尾巴算出来的长度有一截是在播放头背后的。执行层只能把它夹回剩下的部分，
过渡就以一个它从来没有被塑形过的长度出场。

日志里这件事戴的是别人的帽子：`blend clipped to 1.98s of the planned 9s: the next deck took more
than its 1s of lead to start`——那句话把账算在进场 deck 头上，而同一秒里 `blending`、`playSong`、
`blend clipped` 三行是**挨着打出来的**，deck 根本没有慢。慢的是那一眼。
现在 `planTransition` 收一个 `at`（出场曲此刻在第几秒），`left = end - at` 进 ceiling，
`at` 也进 `anchor` 的下限：接多长按真正还剩的时间取整，落点绝不排进过去；真的什么都不剩了就走硬切，
而不是排一个注定被砍的 blend。同时那条日志改成报**测出来的数**，不再替两种成因下结论。

**「控制进场 deck 什么时候起播」是个假问题，真问题是「知道它现在播到哪」。** 这条推翻了文档里两版
P10/P9 的方向。淡入淡出是排在 AudioContext 时钟上的，本来就是采样级精确；不精确的是「排的时候两首
歌各自在第几秒」。`currentTime` 是个台阶，但台阶底下是一条**严格的直线**（斜率就是 playbackRate），
所以拟合一秒的读数就能把相位压到毫秒以下——`deckClock.ts`。有了它，对齐不再需要 AudioBufferSourceNode、
不需要整首解码进内存、不需要重写进度条/拖动/MediaSession，UI 和状态机一行没动。
残留的半个量化步（约 10ms）是常数偏置，两路 deck 同样偏，做差就没了。

**变速只弯出场曲，永远不弯进场曲。** DJ 的做法是反过来的（不能动全场正在跳的那张），但我们这里出场曲
只剩几秒、没有未来可以错，而进场曲马上要被听三分钟——弯了它就得在它独自响着的时候把速度扳回来，
那是整段过渡里唯一没有东西可以遮掩的时刻。

**音高不用我们保，`<audio>` 自己会保——这里曾经保了两遍。** 一度有个 150 行的 WSOLA worklet，
前提是「`playbackRate` 是个重采样器，所以只缺把音高除回去这一半」。这句话对重采样器成立，对媒体元素
不成立：`preservesPitch` 规范默认就是 `true`，元素**自带**时间伸缩器（视频站的倍速用的就是它），
而且它跑在浏览器的音频渲染层，在 Web Audio 取音之前。于是校正被做了两遍——0.75 倍速的出场曲
被整体升高了四度。日志里那句 `outgoing at 0.750x in tune` 的 `in tune` 是假的。
删掉 worklet 之后一起没了的还有：一个独立打包 chunk、音频线程上每 21ms 一次的相关性搜索、
以及每路 deck 永久背着的 20ms 延迟。`tempoBend.ts` 现在只剩两个属性赋值，`preservesPitch` 每次都写，
不吃默认值——它是这条链唯一的前提，写出来才算数。

**「能不能弯到一起」和「能不能叠在一起」是两个阈值，合成一个会出人命。**
`STRETCH_LIMIT` 12%（弯的上限），`DRIFT_LIMIT` 25%（叠的上限），中间那段叫 `drifting`：不弯，
但照叠，只是短。这两个数字各自被定错过一次，两次的错法都值得记：

- 曾经是 25%，等于把弯曲上限压在 5:4 上——而 5:4 和 4:3 正是自相关锁错谐波时返回的比值。
  于是幅度最大的弯曲恰恰是**其中一首测错了**的配对：最大代价，零收益。
- 然后改成 8%，理由是变调推杆的行程。那条理由**是关于音高的**，而音高现在根本不动（浏览器保住了）。
  把一个前提已经消失的约束继续拿来用，结果是 11% 的速度差被判成「两个节奏没法共存」直接切掉——
  日志原话：`blending 0.51s - beatCut - the two tempos are 11% apart, so this one is cut`。
  同一个数字在回答两个问题，降低其中一个的答案就污染了另一个。

现在真正约束弯曲的只剩两条：伸缩器自己的涂抹感（整轨混音上到十分之一还干净），和离谐波比值远一点。
约束叠合的是漂移：最短的 blend 是 4 拍，4 拍漂满一整拍时两个节奏就从「没对齐」变成「打架」，
那是 25%。日志现在**总是**打印实际百分比——`tempos 15% apart, left to drift`——
因为「太远了」这句判词在 11% 和 60% 时长得一模一样，而其中一个是阈值定错了。

同一条规则在过渡长度上被违反过第二次，错法一模一样：出场曲的器乐尾巴和进场曲的前奏，
本来是**两个各自独立的上限**，却被写成 `min(tail, intro)` 一个数——于是**任何一边没测到，
另一边也跟着作废**。一首明明有十秒器乐尾奏的歌，只要进场曲还没被分析过（冷启动后第一次换歌的常态），
就会被横着盖在自己的最后一段副歌上。现在两个窗口各自封顶，两边都知道时仍取较小的那个，
这本来就是那一个数唯一在做的事。

拆开之后还剩最后一层：**这两个窗口是同一条要求的两个代理，而那条要求是「不许两个人声叠在一起」，
不是「淡入淡出期间不许有人声」。** 两个上限同时硬顶，要的就成了后者——比真正的要求严一档，
而且严的是**错的那一档**。`anchor` 的注释自己把话说清楚了：
「两条人声叠在一起是唯一会让重叠听起来不对的事」。

一旦 `tailRoom` 生效，重叠就整段落在出场曲的器乐尾巴里，那一侧**按构造**是不唱的；
这时进场曲开口，是一个人声盖在一段正在退场的器乐上——那不是撞车，那正是这个动作本身。
所以进场窗口只在出场侧**没法为自己作证**时才需要顶：没测到，或者一直唱到自己结束前一秒。

不拆的代价是听得见的：出场曲有 **34.42 秒**器乐尾奏，进场曲第一个段落边界在 2.92 秒，
于是想要 11.88 秒的过渡被 `capped by what the pair has room for (2.92s)` 砍成 **2.04 秒**。
半分钟没有人在唱，而过渡一秒都没分到。现在这种配对会打印
`the next track sings over the outgoing instrumental`——因为这是唯一一处允许过渡越过已测窗口的地方，
听到新歌人声提前进来的人，得能从日志里查到那是有意的。

顺带修掉两个**测不到自己声称在测的东西**的用例：「衰减太长不算结尾」和「从衰减顶点起手」
两条的 fixture 里都放了一句歌词，于是 `max(body, lastSung)` 里真正托住锚点的是人声下限，
不是它们各自的主角。前者的注释写着「而不是 80 秒」，可它根本到不了 80 秒——人声在 150 秒就把底兜住了。
两条都改成 `lines: null`，让被测的那个量成为唯一的输入。

**一首歌被测了两次速度，两次不一致时答案是「不知道」，不是「取后测的那次」。**
`settledBpm(bpm, outroBpm)`：全曲测一次、末 30 秒再测一次，正常情况取后者（收尾渐慢时它才是过渡贴着的
那个速度）。但日志里有 `92 BPM (123 at the end)`、`136 BPM (86 at the end)`——差三分之一到一半，
没有歌会这样慢下来，那是测速在两个窗口里锁到了不同谐波。同一个量测两次对不上，意味着**没测出来**，
返回 null：网格退回实时探针，速度不弯。原来的 `outroBpm ?? bpm` 是无条件相信后测的那次。

**离线分析让主线程歇口气，要按毫秒数，不能按帧数。** `trackProfile` 的扫描曾经是「每 512 帧让一次」，
而「帧」不是一个工作量单位：这里一帧是一次 2048 点 FFT，加上立体声还要再来一次，再加四轮上千个 bin 的
循环。五百帧因此可能是几十毫秒也可能是几百毫秒，取决于曲子和机器——两端都不是一个动画帧的长度，
于是界面**看得见地停住**，一首歌分析期间停二十次。而且只有没分析过的曲子会触发，
所以症状是「过渡后间歇卡顿，但并非每次」。现在是 8 毫秒预算（60Hz 一帧的一半），
查时间而不是数帧数——这才是换台机器也还成立的写法。真要再往上抬，是把扫描搬进 Worker
（`decodeAudioData` 搬不走，但扫描可以收一个转移过去的 Float32Array）。

**测量的失效方式不是「没有答案」，是「给出一个错得很有把握的答案」。** 三处都是这样，
三处的症状都不像测量出错：

- **拍长只精确到一个 hop。** 自相关返回的是整数个 hop，而每个用它的人（小节线、乐句网格、
  入场对齐）都要拿它往外乘几十倍——误差跟着放大。现在做谐波和加抛物线细化，落到 hop 以下。
- **段落边界报的是格子的左边缘。** 自相似矩阵一秒一格，于是真值 5.5 秒报 5.00、8.5 报 8.00，
  误差恒在 [-0.50, 0]——**永不偏晚**，一个方向的系统偏移。三点抛物线取顶点之后降到 ±0.2 秒。
- **前 4 秒是盲区，而盲区不是「报不出来」。** 核在开头伸不满，最早只能从第 5 格起算，
  于是**第一个边界消失、第二个顶上来冒充第一个**：3.0 秒的前奏报 17.00 秒，4.0 秒报 18.00 秒。
  前奏越短、报出来的空间越大——唯一不能弄反的方向。现在核在两端**对称**收缩，
  并除以自己的 taper mass 让不同窗口同尺度（必须对称：左右不等长会让每个边缘格子无脑报高分），
  盲区 5 秒缩到 3 秒。同一轮里小节线也补了从曲头锚定的那一端（`headDownbeatOffset`），
  入场点从它读——只从曲尾锚定的话，前奏那一端要靠推，一首四分钟的歌推过去误差已经没意义了。

改测量必须配合成信号验证：把变化点放在已知时刻上扫一遍，看误差的**符号**分布，
而不是看某一首真歌听起来对不对。上面三条里有两条是靠符号发现的。

**第四种失效方式是闭嘴，而它的成因是一道两边不是同一段音乐的门槛。** 上面三条都是「错得很有把握」，
这条反过来：测量放弃作答。小节线的相位投票只看**最后 24 小节**（网格从曲尾锚定往回推，远端全是外推，
只有近端是直的），而「赢家够不够响」那道门槛拿的却是**整个文件**的平均值。绝大多数歌 `decays out`：
整曲平均里坐着副歌，被量的那段尾巴里没有。于是一记明明在那儿的底鼓，因为没有副歌响，
被判成「这首歌没有小节线」。

代价不是少一个字段，是四个一起没：交接贴不了小节线、乐句对不齐、实时拍格没有、进场只能从 0.00s 进
——这四条 `estimateDownbeat` 的注释里早就写着，只是没人把它和那道门槛连起来读。一份听音日志 9 首里
失败 6 首，全部标着 `decays out`，其中几首速度稳如节拍器；紧接着的一份 3 首全中。两份看着互相矛盾，
其实是**险败与险胜**：合成淡出信号上，赢家舒舒服服高过窗口自己的底噪，却比整曲平均低约 20%。
现在门槛只算那 24 小节。

改完门槛之后实机 9 首里仍有 4 首找不到，比改之前的 6 首好，没有清零。查过一个猜测：
文件尾部的数字静音污染了投票窗口。合成信号上从 0 秒扫到 14 秒尾静音，四个速度全程零变化——
假设站不住，没有据此改代码。**这四首歌为什么找不到，目前不知道。**

日志本身也有个小毛病，顺手补了：小节线其实测了两遍——曲头单独测一遍（前 30 秒，自己的周期），
整曲测一遍（最后 24 小节，整曲的周期）。但曲头那遍的读数只在**整曲那遍也成功**时才打印，
于是恰恰在需要解释的那些曲子上——整曲那遍失败的那些——它一个字都不说，答案其实已经算出来了，
被一个条件判断扣住。改成只要曲头有答案就打印，不改行为，纯粹是把日志里被藏起来的字放出来。
往后 `no bar line found (head 1.98s)` 表示证据在音频里、只是整曲那遍没用上；光秃秃的
`no bar line found` 才是真的没有小节线可读——分清这两种，才好接着查上面那 4 首。
**这条本身不影响播放，优先级低，先放着，等查那 4 首时顺手核对。**

**那一组里四个正向断言一个都不可能失败，这才是它活这么久的原因。** `expect(null).toBeCloseTo(0)`
是**通过**的——`null - 0` 在 JS 里就是 0；写成 `expect(found! % (PERIOD * 4))` 也一样，`null % 2`
还是 0。小节线那一组的正向断言全是这个形状，也就是说它们对「返回了 null」这一种结果完全无感，
而 null 恰恰是这组测试唯一要排除的东西。所以「测试全绿」和「真实曲库里 12 首失败 6 首」可以同时成立。
现在它们都走 `answered()`：先断言有答案，再比对答案。往这个文件加正向断言时先问一句——
**返回 null 会不会让它通过？**

**证据层不认识 React，也不认识播放器。** 新增测量只加在 `trackProfile.ts` / `signalAnalysis.ts`，
它们只接受数组和数字。要拿新数据做决策，改 `transitionChooser` 或 `transitionPlanner`，
不要让执行层直接去读档案。

**改 AudioParam 上正在跑的曲线要用 `cancelAndHoldAtTime`。** `cancelScheduledValues` 只删还没开始的
事件，一条已经在跑的 `setValueCurveAtTime` 会活下来，接着往它的区间里写任何事件都是 NotSupportedError
——而 `settle` 是所有结局的必经之路，中途暂停就会踩到。`crossfadeGraph` 里的 `releaseParam` 是唯一
入口。曲线本身不要在 `startAt` 那一刻再补一个 `setValueAtTime`，引擎会判定重叠。

**一条起点已经过去的曲线不会从过去开始，它只是变长了。** 这条是拿真的 `AudioContext` 问出来的，
不是推的：给 `setValueCurveAtTime` 一个早于 `currentTime` 的起点，引擎把起点**夹到当下**，
**时长照原样保留**——于是结束点跟着往后挪同样多。我们按原起点算出来的复位事件因此落进了
运行中的曲线**内部**，整段三频段整形连同它一起被拒，那一次过渡退成一条平的淡入淡出。
日志里那个 5.33 毫秒的差正好是 48kHz 下的两个渲染量子（主线程晚两个量子，`startAt` 就成了过去时）。
修法是整段调度锚在**夹过之后**的起点上（`Math.max(startAt, context.currentTime)`，
和 `scheduleEchoThrow` 里的 `opensAt` 是同一个动作），复位再往后让 `CURVE_TAIL_GUARD_SEC`：
时钟按量子跳，我们读到的 `currentTime` 可能比引擎一微秒后比对的那个早一格，
而曲线末端是个越界即拒绝、不四舍五入的边界。

这个 bug 能漏出去，是因为**测试替身只记录事件、从不执行引擎规则**——「不许把事件排进运行中的曲线里」
这条从来没有任何测试能看见。`test/unit/automix/fakeAudioGraph.ts` 现在按 Chrome 的边界抛错
（`[起点, 起点+时长)` 左闭右开），`cancelScheduledValues(t)` 丢弃 `start >= t` 的曲线。
往这个替身上加节点时，加的是**规则**，不是又一个记录数组。
